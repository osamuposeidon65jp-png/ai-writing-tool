# セキュリティチェック

この AI ライティングツール（または同じ構成の Streamlit + LLM API アプリ）を診断して、**本当に手を打つべきものが一目で分かるレポート**を書くためのスキルです。

## 前提：脅威モデルを先に決める

このアプリは「個人が自分の PC で使う、DB も認証もないツール」として作られています。大企業向けのチェックリストをそのまま当てはめると「認証がない」「監査ログがない」などの指摘が大量に出て、本当に大事な指摘（たとえば API キーがブラウザ経由で他人に見える）が埋もれてしまいます。

そこで最初に、**どこからアクセスされるか**を確認します。分からなければユーザーに聞くか、「ローカル利用を前提」と明記して進めてください。深刻度はこれで決まります。

| 利用形態 | 主なリスク |
|---|---|
| 自分の PC だけ（localhost） | キーの漏えい（ファイル・ログ経由）、依存パッケージの脆弱性 |
| LAN 上で使う／他の人と共有 | 他人がアプリを開いて、キーの盗み見やクォータの使い込みをする |
| インターネットに公開（Streamlit Community Cloud など） | 上のすべて＋誰でも API 料金を使える状態になる。認証の欠如がはじめて「高」になる |

「認証がない」「DB がない」は設計上の意図です（CLAUDE.md 参照）。ローカル利用なら指摘しないか「情報」扱いにし、公開する場合だけ実害として扱います。

## 手順

### 1. 機械的なスキャン

同梱のスクリプトで、秘密情報の混入・危険なコードの書き方・Streamlit の設定・依存パッケージを一通り洗い出します。

```powershell
.venv\Scripts\python .claude\skills\security-check\scripts\scan.py .
```

スクリプトの結果はあくまで「候補」です。それぞれ実際のコードを読んで、本当に問題か、誤検知かを判断してください。逆に、スクリプトが見つけられない問題（ロジック上の問題）は次の手順で探します。

### 2. コードを読んで確認（観点リスト）

`app.py`、`gemini_client.py`、`prompts.py` を読み、以下を確認します。各観点の背景と具体例は `references/checklist.md` にあるので、判断に迷ったら読んでください。

1. **API キーの扱い**
   - キーがコードや README、`.env.example` に直書きされていないか
   - `.env` が `.gitignore` に入っているか、git 管理されていないか
   - キーがブラウザに送られていないか（`st.text_input(value=os.getenv(...))` は `type="password"` でも値がフロントエンドに渡る）
   - 例外メッセージやログ、`st.cache_data` の引数などからキーが表に出ないか
2. **公開範囲（Streamlit サーバー）**：`server.address`（未設定だと全インターフェースで待ち受ける）、XSRF 保護、`maxUploadSize`
3. **生成結果・入力の描画**：`unsafe_allow_html=True`、`st.html`、`components.html` に LLM の出力やユーザー入力が流れていないか。`st.markdown` は既定で HTML を無効化するので安全側
4. **ファイルアップロード**：形式の制限、サイズ上限、PDF 解析（巨大ファイルや細工した PDF による停止＝DoS）、文字コード
5. **プロンプトインジェクション**：要約するメールや PDF に「以前の指示を無視して…」と書かれていた場合の影響。このアプリの LLM はツールを持たず、テキストを返すだけなので、影響は基本的に「出力がおかしくなる」程度。過大評価しないこと
6. **依存パッケージ**：既知の脆弱性（pip-audit）、バージョン未固定

### 3. 依存パッケージの脆弱性（pip-audit）

```powershell
.venv\Scripts\python -m pip_audit -r requirements.txt
```

`No module named pip_audit` と出たら、勝手にインストールせず、ユーザーに `.venv\Scripts\python -m pip install pip-audit` を実行してよいか確認します（venv に新しいパッケージが入るため）。実行できなかった場合は、レポートの「確認できなかったこと」に書いてください。

### 4. レポートを書く

日本語で、以下の構成で書きます。読み手は個人開発者なので、専門用語には一言説明を添えます。

```markdown
# セキュリティチェック結果

**前提:** <想定した利用形態。例: 自分の PC のみで利用（localhost）>
**総評:** <1〜2文。今すぐ対応すべきものがあるか>

## サマリー
| 深刻度 | 件数 |
|---|---|
| 高 | n |
| 中 | n |
| 低 | n |
| 情報 | n |

## 指摘事項
### [高] <短いタイトル>
- **場所:** `app.py:55`
- **内容:** 何が起きているか
- **なぜ問題か:** 攻撃者や第三者が実際に何をできるか（具体的なシナリオで）
- **修正案:** 差分やコード例

（深刻度が高い順に並べる）

## 問題なしと確認した項目
- 例: `st.markdown` は HTML を描画しない設定のまま。生成結果による XSS の心配なし

## 確認できなかったこと・前提
- 例: pip-audit 未インストールのため、既知の脆弱性は未確認
```

**深刻度の目安**
- **高**：前提の利用形態で、キーの漏えい・任意コード実行・他人による API の利用が現実に起こりうる
- **中**：条件がそろえば起こる（LAN に出たら、など）、または被害が限定的
- **低**：多層防御（守りを重ねておく対策）としてやっておくと良い
- **情報**：問題ではないが知っておくと良いこと

「問題なし」の項目も書いてください。何を確認したかが分かると、ユーザーは安心できますし、見落としにも気づけます。

## 守ること

- **秘密情報の値は絶対に表示しない。** `.env` の中身を `cat` しない。キーが見つかったら、先頭4文字程度とファイル・行番号だけを示す（スクリプトは自動で伏せ字にします）。レポートは共有されることがあるので、そこに本物のキーが載ると、それ自体が漏えいになるからです。
- **既定ではレポートだけ出し、コードは変更しない。** 修正案は示し、「直して」と言われたら直します。直したあとは CLAUDE.md の AppTest によるスモークテストで、全ページが表示できることを確認します。
- **キーの漏えいが疑われたら**、ファイルからの削除だけでなく、Google AI Studio（https://aistudio.google.com/apikey）でのキーの無効化と再発行を勧める。一度外に出たキーは消しても取り戻せないからです。
- 指摘の水増しをしない。件数が多いほど良いレポートではありません。
